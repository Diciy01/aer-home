# AER Remote Gateway и Remote Engine (M14, ADR-017)

Собственная точка входа удалённого доступа на домашнем сервере. Без Tailscale, RustDesk, TeamViewer и чужих серверов. Решение и причины — `docs/adr/ADR-017-remote-engine-gateway.md`.

## Публичный API Gateway (`/gw/v1`, только HTTPS, HTTP/1.1)
Учётка клиента — `Authorization: Bearer aerc1.<clientId>.<secret>`. Ответы — конверт ADR-007 (`{data}` / `{error:{code,message}}`).

| Метод и путь | Назначение |
|---|---|
| `GET /gw/v1/health` | жив ли Gateway (без сведений о системе) |
| `POST /gw/v1/pair` `{code, deviceName}` | одноразовый код сопряжения → учётка клиента (один раз) |
| `GET /gw/v1/hosts` | разрешённые клиенту компьютеры, без адресов LAN и сертификатов |
| `POST /gw/v1/sessions` `{entityId, minutes?}` + `Idempotency-Key` | начать сеанс через ретрансляцию |
| `GET /gw/v1/sessions/{id}` | свой сеанс (чужой — 404) |
| `POST /gw/v1/sessions/{id}/grant` | одноразовая выдача: пароль RDP, сертификат хоста, билеты `rdp`/`files` |
| `POST /gw/v1/sessions/{id}/tickets` `{channel}` | новый одноразовый билет (переподключение), не больше 40 на сеанс |
| `POST /gw/v1/sessions/{id}/end` | завершить сеанс |
| `GET /gw/v1/tunnel` + `Upgrade: aer-tunnel/1` + `X-AER-Ticket` | нога клиента |
| `GET /gw/v1/agent/tunnel?session=&channel=` + `Upgrade` (учётка агента) | нога хоста (паркуется до пары) |
| `/gw/v1/agent/api/v1/…` | прокси для агентов вне LAN: **только** `remote/agent/hello`, `remote/agent/commands`, `remote/agent/sessions/{id}/events`, `monitoring/agent/report` |

Протокол ноги: запрос `GET` с `Connection: Upgrade`, `Upgrade: aer-tunnel/1` → `101 Switching Protocols` → непрозрачный поток. Ноге хоста Gateway при появлении пары пишет байт `0x01`, после чего агент соединяет её с `127.0.0.1:<порт RDP|файлов>` и паркует следующую ногу.

## Авторизация
1. Владелец (AER HOME в LAN, токен владельца): `POST /api/v1/remote/clients {name, hosts[], clipboard, files}` → код `XXXX-XXXX-XXXX` (15 мин, один раз). Повторное сопряжение — `POST /remote/clients/{id}/pairing` (старая учётка перестаёт работать). Отзыв — `POST /remote/clients/{id}/revoke` (сеансы клиента → `revoked`, туннели закрываются).
2. Клиент: адрес сервера + код. Перед вводом кода клиент показывает отпечаток сертификата Gateway (`probeFingerprint`), пользователь сверяет его с выводом `aer-remote-gateway -fingerprint` — затем отпечаток закрепляется. В AER Connect профиль и учётка `aerc1` хранятся вместе в отдельном DPAPI-хранилище (M14.4), owner token не используется. Инструкция — `AER_CONNECT.md`.
3. Gateway → Core: служебная учётка агента вида `gateway` (`POST /api/v1/monitoring/agents {"kind":"gateway"}`) + учётка клиента в `X-AER-Remote-Client`. Core проверяет обе; Gateway ничего не решает сам.
4. Права сеанса = хост ∩ политика владельца ∩ права клиента ∩ запрос. Билеты: 256 бит, только SHA-256 в памяти Core, 60 с, одно использование (неудачная попытка тоже сжигает билет), привязаны к сеансу, клиенту и каналу, стираются при завершении сеанса.
5. Ограничения попыток: Core блокирует клиента на 15 мин после 5 неверных секретов за 10 мин; Gateway банит адрес на 15 мин после 10 неудач (неверная учётка, билет) за 10 мин и пропускает не больше 5 попыток сопряжения с адреса за 10 мин. Ответы на «нет клиента», «неверный секрет», «отозван», «заблокирован» одинаковы.

## Развёртывание (когда владелец решит открыть доступ)
Ничего из этого не делается автоматически.
1. Собрать: `go build -o bin/aer-remote-gateway ./cmd/aer-remote-gateway` (из `core/`).
2. В AER HOME создать учётку агента вида `gateway`, привязанную к сущности сервера; положить токен в файл с правами 0600.
3. Конфиг по образцу `deploy/remote-gateway.example.json`: `coreUrl` — Core на этом же сервере (`http://` разрешён только к loopback), `listenAddr` — например `0.0.0.0:8443`.
4. `aer-remote-gateway -config … -fingerprint` — отпечаток для клиентов и агентов.
5. Агентам хостов добавить `gatewayUrl` (тот адрес, который видят клиенты) и `gatewayCertSha256`. Агенту вне LAN (рабочий ПК) — ещё `coreUrl: https://<адрес>/gw/v1/agent` и `coreCertSha256`.
6. На роутере владелец **сам** пробрасывает **один** порт: WAN 443/TCP → сервер:8443. Ничего больше: Core 8787, RDP 3389, файлы 3390, SSH, БД — не пробрасываются.
7. Адрес для клиентов: статический IP, имя DDNS или собственный домен — вводится пользователем в клиенте, в приложениях не зашит.

## AER HOME: клиенты и подключение через Gateway (M14.5, 2026-10-28)
- **«Удалённый доступ» → «Клиенты»** (владелец, через Core): карточка Gateway с его отпечатком (Gateway сообщает его Core при запуске и раз в минуту — `POST /remote/gw/info`, `GET /remote/gateway`), создание клиента (имя, компьютеры, буфер, файлы), одноразовый код — показывается один раз и нигде не хранится, новый код, права, отзыв с подтверждением.
- **«Удалённый доступ» → «Через Gateway»** (работает без Core, вне дома): адрес сервера (IP/DDNS/домен) → «Проверить сертификат» (только TLS-рукопожатие) → отпечаток SHA-256 и сравнение с известным Core → флажок «Отпечаток совпадает — закрепить» → код → список разрешённых компьютеров → сеанс через Gateway во встроенном просмотре (внешний клиент — запасной), файлы по туннелю, «Завершить», понятные сообщения (несовпадение сертификата, отзыв, ограничение попыток, сервер недоступен).
- Учётка клиента — в хранилище ОС (`flutter_secure_storage`: libsecret на Linux, DPAPI-encrypted storage на Windows; настоящий DPAPI round trip проверен в M10 отдельным тестовым ключом). Профиль (адрес, отпечаток, имя клиента) — без секретов. На стенде — отдельный файл (`AER_REMOTE_SECRET_STORE=file` вместе с `AER_DESKTOP_DATA_DIR`; 0600 на POSIX), чтобы тесты сопряжения не трогали действующую учётку ОС.
- Протокол — только общий движок `packages/aer_remote`; страница рабочего стола общая для LAN и Gateway.
