# ADR-018: AER Connect Anywhere — устройства по ID и паролю

Статус: принято 2026-10-29 (M14.4). Контракт 0.12.0, аддитивно к ADR-017.

## Контекст

ADR-017 дал собственный Gateway (`aer-tunnel/1`, один публичный TLS-порт) и
клиентов, которых владелец создаёт вручную со списком разрешённых хостов.
Нужна модель «как RustDesk», но на своём сервере: установил приложение,
увидел ID и пароль, ввёл их на другом ПК — подключился. Любая установка
одновременно Host и Viewer. Клиенты в любых сетях (NAT, CG-NAT, мобильный
интернет), публичный адрес только у домашнего Ubuntu Server. Без VPS,
RustDesk-серверов, Tailscale, ZeroTier и чужих ретрансляторов.

## Решение

1. **Устройство** = одна установка AER Connect = сущность Registry
   (`computer`, тег `aer-connect`) + учётка агента `remote` (Host) + учётка
   клиента `aerc1` (Viewer) + публичный 9-значный номер. Таблица
   `remote_devices`. Номер не секрет; он не даёт ни входа, ни перерегистрации.
2. **Регистрация** только по коду владельца (`/remote/enrollments`, N
   устройств, срок до 30 суток, хранится SHA-256). Анонимная регистрация
   отвергнута: Gateway смотрит в интернет, а устройство получает учётку
   агента. Код вводится один раз; адрес и отпечаток Gateway могут прийти из
   `connect.json` установщика. Ошибки «нет кода/истёк/исчерпан/отозван»
   неразличимы. Лимит Gateway — как у сопряжения (5 попыток/10 мин/адрес).
3. **Пароль проверяет Host, а не сервер.** Устройство при регистрации
   сообщает открытый X25519-ключ. Viewer просит у Core одноразовую попытку
   (`challenge`: attemptId 128 бит, 60 с, привязка к viewer и цели) и
   отправляет пароль, запечатанный: X25519(эфемерный, ключ Host) → HKDF-SHA256
   (salt = SHA-256(attemptId), info = версия, номера сторон, оба открытых ключа)
   → AES-256-GCM (AAD = attemptId), внутри метка времени. Core и Gateway
   пересылают шифротекст и не могут ни прочитать пароль, ни перебрать его
   офлайн. Попытка одноразовая в Core (сжигается и при отказе) и на Host
   (множество увиденных id); перенос шифротекста в другую попытку, к другому
   viewer или Host не открывается.
4. **Вердикт до согласия.** Core создаёт сеанс с `auth_state=required` и
   команду `open` с `auth`; Host отвечает `auth_ok`/`auth_failed` до
   локального диалога. Пока вердикта нет, Core отвергает
   `awaiting_approval/approved/ready` — агент не может пропустить проверку.
   `POST /connect` отвечает после вердикта: «неверный пароль» — понятная
   ошибка, а не упавший сеанс. Сеанс без пароля к устройству Core отвергает
   (`device_password`), даже если владелец добавил устройство клиенту.
   Core не шлёт попытки хосту без `features: ["connect-auth/1"]`.
5. **Пароли.** Временный: 8 символов без похожих (≈39,6 бит), только в
   памяти Host, новый при каждом запуске, после сеанса, по кнопке, после Stop
   и после блокировки. Постоянный: выключен по умолчанию, ≥10 символов и ≥6
   разных, хранится PBKDF2-SHA256 600 000 итераций (соль 16 байт) в DPAPI
   профиле приложения. Ни один пароль не проходит через логи Core/Gateway.
6. **Лимиты.** Core: 30 challenge/10 мин на viewer; 5 неверных паролей
   viewer→устройство и 20 к устройству от всех → блок 15 мин (+ событие).
   Host: 5 неверных за 10 мин → блок 15 мин и смена временного пароля.
   Gateway: прежний бан адреса за неудачные учётки/билеты.
7. **Локальное согласие и Stop сохраняются для любого режима**, включая
   постоянный пароль. Неприсмотренный доступ без подтверждения в этом выпуске
   не предоставляется: модель безопасности M14.4 (видимое согласие, видимый
   Stop, завершение при lock/UAC) имеет приоритет.
8. **Клонирование.** Host сообщает `instance` = SHA-256(installId, MachineGuid).
   Другой `instance` с той же учёткой → устройство помечается `conflict`,
   входящие сеансы запрещены; лечится отзывом и новой регистрацией. DPAPI
   CurrentUser к тому же не расшифрует профиль на другой машине/учётке.
9. **Транспорт без изменений**: только relay через свой Gateway (ADR-017),
   Host открывает исходящие TLS-ноги, RDP/files — loopback. P2P/hole punching
   не делаются; это возможная будущая оптимизация, не требование.
10. **Процесс Host.** `aer-connect-host` — дочерний процесс AER Connect,
    JSON-строки по stdin/stdout; секреты (токен агента, ключ X25519,
    верификатор) приходят в первой строке и не пишутся на диск. Закрытие stdin
    останавливает Host и закрывает сеанс. Отказ запуска с повышенными правами.

## Последствия

- Владелец видит устройства в `/remote/devices` и в обычном списке хостов;
  может отозвать устройство (обе учётки, все сеансы, номер не переиспользуется).
- Существующее сопряжение (`aerc1`, списки хостов) не меняется и продолжает
  работать для обычных `aer-remote-host`; устройство-Viewer тоже клиент `aerc1`.
- Скомпрометированный Core мог бы подменить ключ Host (он корень доверия
  всей системы); от компрометации Gateway без Core пароль защищён.
- Требуется мигрировать БД Remote до версии 3 (аддитивно).
