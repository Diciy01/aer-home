# ADR-013: Удалённый доступ — RDP как транспорт, Core как плоскость управления (M07)

**Статус:** ACCEPTED (2026-10-27). Основание — `docs/S_REMOTE_FEASIBILITY.md`. Контракт 0.7.0 → **0.8.0** (аддитивно: `/remote/*`). Закрывает ADR-003 «Remote provider».

## Контекст
Нужен удалённый рабочий стол Windows↔Ubuntu, Ubuntu↔Ubuntu, Windows↔Windows, позже — отдельные приложения с телефона. Хост Ubuntu работает под GNOME Wayland (без скрытого захвата и ввода). Core — слабый домашний сервер: видео через него не идёт. Нельзя: свой видеопротокол при наличии готового, копирование AGPL-кода, проброс портов в интернет, один токен на все устройства.

## Решение
1. **Транспорт — RDP.** Хост Ubuntu: `gnome-remote-desktop` (Wayland-нативный, TLS + NLA, проверен на стенде: экран, мышь, клавиатура, текстовый буфер в обе стороны, отзыв за ≈100 мс). Хост Windows: встроенный RDP (Pro/Enterprise). Клиент Linux: **внешний** Remmina (FreeRDP 3), клиент Windows: **внешний** `mstsc`. Встраивание RDP-клиента во Flutter отложено (FreeRDP через FFI — отдельный проект); интерфейс прямо говорит «изображение в окне Remmina/Подключения к удалённому рабочему столу».
2. **Core — только плоскость управления** (модуль `remote`): хосты (поверх Registry), политики, сеансы и их состояния, одноразовая выдача данных подключения клиенту, отзыв, аудит, интеграция с Monitoring. Видео, ввод, буфер обмена и файлы идут клиент ↔ хост напрямую.
3. **Агент хоста `aer-remote-host`** с отдельными учётными данными устройства (агент Monitoring вида `remote`, `aer1.<id>.<secret>`, отзывается мгновенно). На каждый одобренный сеанс агент: (по политике) спрашивает согласие на хосте → генерирует случайный пароль RDP → `grdctl rdp set-credentials` + `enable` → сообщает Core пароль и сертификат. По завершении, отзыву, истечению срока или потере связи с Core после истечения — `disable` + `clear-credentials`. **Порт RDP слушается только во время сеанса.** Agent long-poll'ит Core; Core не подключается к агентам.
4. **Выдача данных подключения**: клиент (токен владельца) получает их `POST /remote/sessions/{id}/grant` **один раз** и в течение 60 с после готовности; пароль хранится только в памяти Core и стирается при выдаче. Повторная выдача — 410. Сертификат хоста клиент кладёт в хранилище FreeRDP (`freerdp/server/<host>.<port>_<port>.pem`) — подмена хоста приводит к отказу TLS.
5. **Файлы — собственный канал AER**: HTTPS прямо к агенту хоста (тот же закреплённый сертификат), токен сеанса, только папка обмена агента, лимит размера, SHA-256 в заголовке, проверка до переименования временного файла. Через Core файлы не идут.
6. **Состояния сеанса**: `pending → awaiting_approval → connecting → connected ⇄ reconnecting → disconnected | failed | expired | revoked`. «Подключён» — по факту установленного TCP-соединения с портом RDP, который видит агент (не по словам клиента).
7. **Политика**: эффективные права = (что заявил хост в своём конфиге) ∩ (политика владельца в Core). Не больше одного активного сеанса на хост, общее ограничение сеансов, срок сеанса (по умолчанию 60 мин, максимум 8 ч), срок ожидания согласия.
8. **Потеря Core**: установленный RDP-сеанс от Core не зависит. Агент сам завершает сеанс по сроку `expiresAt`, полученному при открытии, даже без Core; отзыв требует связи агента с Core (агент опрашивает каждые ≤25 с).
9. **Remote Apps** (мобильные): модель и API (`GET /remote/hosts/{id}/apps` → `UNSUPPORTED` с причиной) без имитации. RDP GNOME не поддерживает RemoteApp; портал даёт захват окна, но не ограничивает ввод окном — изоляцией это не является.

## Альтернативы
- RustDesk — AGPL-3.0 (встраивание раскрывает весь AER), собственный ретранслятор; на Wayland тот же портал с диалогом. Может стать внешним адаптером.
- Собственный транспорт портал + PipeWire + WebRTC — нужен для Remote Apps, но это собственный видеопротокол; отложено до мобильного этапа.
- Sunshine/Moonlight — нет буфера и файлов, используется пользователем для ТВ.
- MeshCentral — тяжёлый Node.js-сервер; VNC в GNOME 46 удалён.

## Последствия
- Windows-хост и клиент `mstsc` — UNVERIFIED до проверки на Windows (`docs/REMOTE_WINDOWS_VALIDATION.md`); пароль Windows-сеанса — учётная запись пользователя (агент его не меняет).
- Пароль сеанса проходит через Core: Core↔агент и Core↔клиент должны идти по loopback или защищённой сети (Tailscale/VPN). По открытому HTTP в LAN пароль сеанса виден слушающему сеть (короткоживущий, одноразовый) — ограничение до TLS для Core.
- Отключение буфера обмена на сеанс — только на стороне клиента (сервер GNOME не умеет).
