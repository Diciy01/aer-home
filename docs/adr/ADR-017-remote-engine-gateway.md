# ADR-017: Remote Engine, собственный Gateway и AER Connect (этап M14)

**Статус:** ACCEPTED (2026-10-28). Развивает ADR-013 (M07), не отменяет его. Контракт Core 0.10.0 → **0.11.0** (аддитивно: клиенты удалённого доступа, служебный API Gateway). Новый публичный протокол Gateway — `docs/REMOTE_GATEWAY.md`.

## Контекст
M07 дал рабочий удалённый доступ в LAN: Core — плоскость управления, агент `aer-remote-host` включает RDP (gnome-remote-desktop) только на время сеанса с паролем на сеанс и закреплённым сертификатом, изображение — во внешнем клиенте (Remmina/mstsc). Нужно:
1. подключаться из интернета (работа → дом) **без** Tailscale, RustDesk, TeamViewer и чужих серверов — только через домашний сервер владельца;
2. лёгкий самостоятельный клиент **AER Connect** (сначала Windows) и встроенный просмотр в AER HOME — на **одном** движке;
3. хост Windows Home, где встроенного RDP-сервера нет;
4. ничего, кроме одного защищённого порта Gateway, не открывать в интернет.

Нельзя: свой криптографический протокол, свой видеокодек, копирование AGPL-кода, общий токен на всех клиентов, порты RDP/SSH/Core/агентов в интернете.

## Решение

### 1. Компоненты и границы доверия
```
 Интернет                    │ Домашний сервер (Ubuntu)                 │ LAN / исходящие
                             │                                          │
 AER Connect ──TLS 443──────►│ aer-remote-gateway ──loopback HTTP──► aer-core (remote)
 (Windows, рабочий ПК)       │   • TLS, закреплённый сертификат         │      ▲ long-poll
                             │   • учётка клиента → проверяет Core      │      │ (агентская учётка)
 AER HOME (дома, в LAN) ─────┼──── напрямую к Core (как в M07) ─────────┤      │
                             │   • ретранслятор «aer-tunnel/1»  ◄──TLS──┼── aer-remote-host
                             │     (склеивает ногу клиента и            │   (дом. ПК / рабочий ПК,
                             │      ногу хоста, видит только шифртекст) │    только исходящие)
```
- **Core** остаётся единственным источником правды: хосты (Registry), политики, сеансы, аудит, **клиенты удалённого доступа и их права**, одноразовые билеты туннеля. Gateway не хранит ни реестра, ни учёток.
- **aer-remote-gateway** — отдельный процесс на сервере, единственный компонент, доступный из интернета. Сам по себе он ничего не решает: каждый запрос клиента проверяется в Core (служебная учётка Gateway + учётка клиента). Хранит в памяти только активные туннели.
- **aer-remote-host** (M07) — тот же агент. Новое: «нога ретрансляции» — **исходящее** TLS-соединение к Gateway на время сеанса; агент сам соединяет её с локальным RDP-сервером и каналом файлов на 127.0.0.1. Входящих портов хосту не нужно (сценарий B: рабочий ПК за NAT/корпоративным файрволом).
- **Remote Engine** — общая реализация протокола, без интерфейса:
  - Go `core/internal/remoteengine`: модель (состояния сеанса, права, команды агенту, события, выдача), протокол туннеля (`Dial`/`Accept`/`Splice`), закрепление TLS. Используют Core, Gateway и агент.
  - Dart `packages/aer_remote`: клиент Core/Gateway, модель сеанса, учётка и закрепление сервера, локальный туннельный порт 127.0.0.1, канал файлов, интерфейс `RemoteViewer`. Используют AER HOME и AER Connect.
  - Платформенные адаптеры: хост — `Backend` (gnome-rdp, windows-rdp, windows-shadow), клиент — `RemoteViewer` (external-rdp сейчас, embedded-freerdp — подэтап M14.3).

Граница доверия: интернет ↔ Gateway (TLS + учётка клиента + билет); Gateway ↔ Core — loopback на одном сервере, служебная учётка; Core/Gateway ↔ агент — учётка агента. Изображение, ввод, буфер и файлы идут **сквозным** TLS клиент ↔ хост (RDP TLS/NLA с закреплённым сертификатом хоста; канал файлов — HTTPS агента с тем же сертификатом): Gateway их не расшифровывает. Пароль сеанса RDP проходит через Core и Gateway (оба — сервер владельца, одна зона доверия) и в журналы не пишется.

### 2. Транспорт изображения и ввода — RDP остаётся
Протокол на проводе — RDP, как в M07: проверен на GNOME Wayland, кодеки (RemoteFX/GFX/H.264) и шифрование — готовые (gnome-remote-desktop, FreeRDP). Один клиентский стек и один тип ретрансляции (непрозрачный байтовый поток) на все ОС хоста. Свой видеопротокол (портал + PipeWire + WebRTC) отвергнут на этом этапе: он заменил бы проверенный M07 большим объёмом нового кода на каждой ОС (захват, кодирование, инъекция ввода) без выигрыша для desktop-сценариев; остаётся вариантом для мобильных Remote Apps (ADR-013 п.9).

### 3. Хосты по ОС
| ОС хоста | Адаптер | Учётные данные | Статус |
|---|---|---|---|
| Ubuntu GNOME (Wayland) | `gnome-rdp` (M07) | пароль на сеанс | VERIFIED в M07 (стенд) |
| Windows Pro/Enterprise | `windows-rdp` (M07, readiness probe) | предполагается учётная запись Windows (NLA); управляемого AER-сеанса ещё нет | M10: ready=false / Open отказывает, пока не реализованы настоящий сертификат, права и отзыв; реализация Host → M14.4 |
| Windows Home (и Pro без блокировки консоли) | `windows-shadow`: собственная DXGI/SendInput-подсистема поверх FreeRDP server/shadow (Apache-2.0), текущий обычный пользователь, локальное согласие и Stop | случайный пароль через анонимный stdin, TLS-сертификат/ключ на сеанс; без SAM-файла и Windows logon | **IN_PROGRESS M14.4**: код и настоящий RDP с SYNTHETIC источником проверены на Windows; реальная DXGI/SendInput-приёмка BLOCKED до отдельного согласия/обычного пользовательского процесса |
Встроенный RDP на Windows Home отсутствует — это не предполагается. Если shadow-подсистема FreeRDP окажется непригодной, запасной путь — серверная библиотека FreeRDP (`libfreerdp-server3`) с собственным захватом DXGI и `SendInput` за тем же интерфейсом `Backend`; кодеки остаются из FreeRDP.

Реализация 2026-10-29 выбрала этот запасной путь: `native/aer_shadow` не
собирает upstream Windows WDS/CLI, но переиспользует server/shadow API.
RDP слушает только 127.0.0.1, Windows backend требует relay и prompt,
отвергает службу/session 0/elevated/UIAccess/secure desktop. Lock/UAC/DXGI
access-lost и native deadline прекращают доступ без автоматического возобновления.
Контракт 0.11.1 добавляет `windows-shadow` без смены wire-протокола/миграции БД;
старые backend и внешние клиенты сохраняются. Сначала обновляются Core/агент,
затем выбирается новый backend в конфиге; старый Core не рекламирует его.
Ограничения и незавершённая реальная приёмка: `../WINDOWS_HOST.md`,
`../M14_4_REPORT.md`. Наличие синтетического теста не подтверждает DXGI/SendInput.

### 4. Встроенный просмотр (M14.3) — FreeRDP 3 через FFI
Оценка библиотек:
| | FreeRDP 3 (`libfreerdp-client3`) | IronRDP |
|---|---|---|
| Лицензия | Apache-2.0 | MIT/Apache-2.0 |
| Зрелость | основа Remmina/Ubuntu, проверен в M07 против gnome-remote-desktop (GFX) | молодой, поддержка конвейера GFX, нужного gnome-remote-desktop, не подтверждена |
| Linux | библиотеки 3.32 уже в системе; нужны заголовки (`freerdp3-dev`, установка — с согласия владельца) | cargo есть |
| Windows | сборка CMake/vcpkg (M10) | cargo |
| Внешний сервер | не нужен | не нужен |
Решение: тонкая C-прослойка `aer_rdp` над `libfreerdp-client3` (кадр BGRA → текстура Flutter, события мыши/клавиатуры, cliprdr для текста) и Dart FFI. IronRDP — запасной вариант, если сборка FreeRDP под Windows окажется непосильной. До готовности встроенного просмотра используется **внешний** клиент (fallback): Remmina/mstsc подключаются к локальному порту движка 127.0.0.1 — ретрансляция через Gateway работает и с ним.

### 5. Авторизация
- **Клиент удалённого доступа** (AER Connect на рабочем ПК, другой ПК с AER HOME вне дома) — отдельная запись в Core: имя, **список разрешённых хостов**, права (буфер, файлы), срок, отзыв. Учётка `aerc1.<id>.<secret>` (256 бит, в Core только SHA-256), у каждого клиента своя.
- **Сопряжение:** владелец в AER HOME (LAN, токен владельца) создаёт клиента → Core выдаёт **одноразовый код сопряжения** (≈60 бит, 15 мин, хранится хэшем). В AER Connect: адрес сервера + код; приложение показывает отпечаток SHA-256 сертификата Gateway, пользователь сверяет его с показанным в AER HOME → учётка выдаётся один раз и хранится в защищённом хранилище ОС (Windows DPAPI/Credential Manager, Linux libsecret).
- **Gateway** — служебная учётка агента Monitoring вида `gateway` (тот же механизм `aer1.<id>.<secret>`, мгновенный отзыв). Маршруты Core `/remote/gw/*` принимают **только** её и требуют учётку клиента в `X-AER-Remote-Client`.
- **Ограничение попыток:** Gateway — по IP (неудачи → блокировка), Core — по идентификатору клиента (блокировка после серии неудач). Ответ на неверную учётку не различает «нет клиента»/«неверный секрет»/«отозван».
- **Краткоживущие разрешения:** выдача (grant) по-прежнему одноразовая; вместо адреса хоста клиент получает **билеты туннеля** — по одному на канал (`rdp`, `files`): случайные 256 бит, только хэш в памяти Core, 60 с, **одно использование**, привязка к сеансу, клиенту и каналу. Для переподключения клиент запрашивает новый билет (только для своего незавершённого сеанса, с лимитом).
- Права сеанса = (заявлено хостом) ∩ (политика владельца) ∩ (права клиента) ∩ (запрос).

### 6. Установление соединения (ретрансляция)
1. Клиент → Gateway `POST /gw/v1/sessions {hostId}` → Core создаёт сеанс (`route=relay`), агент получает команду `open` с `relay: true`.
2. Агент готовит RDP (как в M07), сообщает `ready` и **паркует** ноги туннеля: исходящее `GET /gw/v1/agent/tunnel?session=…&channel=rdp|files` с `Upgrade: aer-tunnel/1` и своей учёткой; Gateway проверяет у Core, что сеанс принадлежит хосту агента и активен.
3. Клиент → `POST /gw/v1/sessions/{id}/grant` → пароль RDP, закреплённый сертификат хоста, билеты.
4. Движок клиента открывает 127.0.0.1:случайный порт; просмотрщик подключается к нему; движок открывает `GET /gw/v1/tunnel` (`Upgrade: aer-tunnel/1`, учётка клиента + билет). Gateway погашает билет в Core, находит припаркованную ногу хоста, отправляет хосту байт «начали», отвечает клиенту `101` и склеивает потоки. Агент соединяет свою ногу с 127.0.0.1:<порт RDP|файлов> и паркует новую ногу (переподключение, второй TCP).
5. Внутри — сквозной RDP TLS/NLA с закреплённым сертификатом; Gateway видит только шифртекст и считает байты.

Транспорт туннеля — HTTP/1.1 `Upgrade: aer-tunnel/1` поверх TLS (как WebSocket, но без кадрирования): поддерживается стандартными библиотеками Go (`net/http` hijack, `101` с `io.ReadWriteCloser`) и Dart (`HttpClientResponse.detachSocket`), новых зависимостей нет; через HTTP CONNECT-прокси проходит так же, как WebSocket. Если корпоративный прокси потребует WebSocket — это отдельный адаптер транспорта, протокол сеанса не меняется.

**Сценарий C (LAN):** AER HOME, подключённый к Core в LAN, использует прямой путь M07 (`route=direct`, адрес хоста в LAN) — трафик через сервер не идёт. Автоматический выбор прямого пути для AER Connect в той же LAN — позже (нужна проверка, что клиент действительно в LAN, а адрес хоста не подменён; сертификат закреплён в любом случае).

**P2P/NAT traversal не делается:** ретрансляция через собственный Gateway — единственный путь из интернета в первой версии; это проще и безопаснее (один открытый порт, вся авторизация в одном месте).

### 7. Сеть
- Открыть в интернет только порт Gateway: WAN 443/TCP → сервер:8443 (проброс на роутере — **владелец вручную**, AER роутер не меняет). Core (8787), RDP (3389), файлы агента (3390), SSH — только LAN/loopback.
- Адрес сервера — строка, которую вводит пользователь: статический IP, имя DDNS или собственный домен. В приложении не зашит.
- Сертификат Gateway: самоподписанный (создаётся при первом запуске) или свой (например, полученный владельцем через ACME). В обоих случаях клиент **закрепляет** отпечаток при сопряжении; чужой сертификат → отказ.

### 8. Файлы и буфер
- Файлы — канал M07 (HTTPS агента, токен сеанса, папка обмена, лимит размера, SHA-256), через туннель `files`; разрешение проверяет Core (выдача билета `files` только если `allowed.files`), агент (поднимает канал только при `allowed.files`) и сервер файлов (токен).
- Буфер — канал RDP cliprdr; отключение на сеанс — на стороне клиента (gnome-remote-desktop не умеет), встроенный просмотрщик обязан соблюдать `allowed.clipboard`.

### 9. Обрыв, зависшие сеансы, отзыв
- Сеанс: состояния M07; потеря соединения → `reconnecting` (агент видит закрытие TCP) → новый билет → переподключение в пределах `reconnectGraceSec`.
- Gateway раз в несколько секунд сверяет активные туннели с Core и закрывает туннели завершённых/отозванных сеансов; простаивающие туннели и припаркованные ноги закрываются по тайм-ауту.
- Отзыв клиента → все его сеансы `revoked`, туннели закрываются, учётка больше не принимается. Отзыв служебной учётки Gateway → Gateway перестаёт обслуживать всех.
- Потеря Core: новые сеансы невозможны; Gateway закрывает туннели, если Core не отвечает дольше порога; агент завершает сеанс по `expiresAt` сам (M07).

## Альтернативы
- WebRTC (pion + flutter_webrtc + свой TURN в Gateway): единый стек для мобильных, но собственный захват/кодирование/ввод на каждой ОС и отказ от проверенного M07. Отложено (Remote Apps).
- Проброс RDP-порта/SSH в интернет — запрещено.
- Gateway как обратный прокси ко всему API Core — отвергнуто: в интернет попал бы API владельца.
- WebSocket вместо `aer-tunnel/1` — нужна библиотека в Go; выигрыша нет, пока нет прокси, требующих WebSocket.
- mTLS вместо учётки-носителя — сильнее (без сертификата клиента TLS не устанавливается), но сложнее для Dart и тестов; запланировано как усиление после M14.

## Последствия
- Этап **M14** (после M10; отменённый M11 не является зависимостью): M14.1 Engine, M14.2 Gateway, M14.3 встроенный просмотр, M14.4 AER Connect (Windows), M14.5 интеграция в AER HOME. Части без Windows (M14.1–M14.3 на Linux) можно делать до M10; всё, что касается Windows, — UNVERIFIED до проверки на Windows.
- Схема не считается готовой, пока нет рабочих Engine, Gateway и самостоятельного AER Connect.
- Через интернет функция не считается готовой, пока Gateway не прошёл проверку TLS/ограничений попыток/отзыва на стенде и владелец не открыл порт сам.
- Риски: Windows shadow-сервер FreeRDP; сборка FreeRDP под Windows; mstsc не умеет закреплять сертификат (fallback показывает отпечаток для ручной сверки) и может отказаться подключаться к 127.0.0.1 (используется 127.0.0.2); корпоративные прокси/DPI на рабочем ПК; кириллица с клавиатуры (UNVERIFIED с M07); пропускная способность домашнего аплинка при ретрансляции.
