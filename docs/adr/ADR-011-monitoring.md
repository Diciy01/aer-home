# ADR-011: Мониторинг (M05)

**Статус:** ACCEPTED (2026-10-27). Контракт `openapi.yaml` 0.5.0 → **0.6.0** (аддитивно: новые пути `/monitoring/*`, схема `agentAuth`; черновой `/incidents` из 0.4.0 заменён).

## Контекст
Нужно видеть состояние домашней инфраструктуры (ПК с двумя ОС, будущий сервер, сеть, Docker, боты), историю, журналы, инциденты и уведомления — на маломощном сервере (ориентир 4 ГБ RAM), без тяжёлых компонентов, с данными только из реальных источников. Сбор должен идти без открытого клиента.

## Решения
1. **Модуль Core `monitoring`** в существующем монолите. Свои таблицы `mon_*`; Registry читается только через `registry.Reader` (передаётся при сборке модулей); в Registry ничего не пишется. Фоновая работа — через новый необязательный интерфейс Foundation `module.Runner` (живёт столько же, сколько Core).
2. **Хранение в SQLite** (без отдельной TSDB): сырые значения `mon_samples` (WITHOUT ROWID, ключ сущность/метрика/метка/время) 7 дней; 5-минутные агрегаты `mon_rollups` пишутся **в той же транзакции**, что и сырое значение, хранятся 30 дней, поэтому очистка сырых данных не теряет историю графиков; `mon_latest` — текущее значение каждой серии, не очищается; `mon_state` — состояние устройства. Все сроки и лимиты — в конфигурации.
3. **Протокол агента v1**: один `POST /monitoring/agent/report` (heartbeat + метрики + логи, пакеты до 2000/500). Метрики — только из каталога (`GET /monitoring/metric-types`), значение `null` обязано иметь `quality = unsupported|unavailable` и причину: отсутствие данных никогда не превращается в 0.
4. **Учётные данные агентов**: отдельный токен на каждого агента `aer1.<agentId>.<secret>`, в базе только SHA-256 секрета, сравнение за постоянное время, мгновенный отзыв. Сущность берётся из учётных данных, а не из тела запроса — агент не может выдать себя за другое устройство. Маршрут агента принимает только такие токены (новый `httpapi.Authorize`), маршруты владельца — только токен владельца. Секреты не передаются в URL (исключение: Telegram Bot API, где токен в пути — требование API; URL нигде не логируется).
5. **Состояния** online / degraded / offline / unknown / unsupported. Источник по типу: агент (heartbeat), heartbeat бота, HTTP, TCP-достижимость, Docker. Гистерезис: «недоступен» — только после N подряд неудачных проверок и только для цели, которая раньше отвечала; цель, ни разу не ответившая, остаётся «неизвестно» (TCP/ICMP-молчание не доказывает выключение). Отказ в соединении = хост в сети. ICMP не используется (нужны привилегии). Устройство «в сети», если отвечает **любой** из его агентов (dual boot: неактивная ОС — не тревога).
6. **Инциденты**: ключ группировки (`availability:<id>`, `disk_low:<id>:<mount>`…), не больше одного нерешённого инцидента на ключ (частичный уникальный индекс), повторы увеличивают счётчик; подтверждение пользователем; автозакрытие после подтверждённого восстановления; пороги с антидребезгом (N замеров подряд) и гистерезисом. `cause` заполняется только из прямых данных (код выхода Docker, OOMKilled, HTTP-статус); связь с инцидентами зависимостей (через связи Registry) хранится отдельно как корреляция.
7. **Логи**: централизованная таблица с уровнями, источником, корреляцией, ссылкой на инцидент; вырезание секретов **до записи**; лимит на источник (записей/мин) и общий лимит строк; предупреждения/ошибки самого Core попадают туда через неблокирующий `logging.Sink`.
8. **Уведомления**: внутренний центр — одно уведомление на открытие/восстановление инцидента, не на замер. Telegram — выключен по умолчанию, токен из файла, сообщения группируются за цикл отправки.
9. **Docker** — только чтение через локальный сокет (TCP-сокет запрещён конфигурацией), без управления контейнерами.
10. **Агент** — отдельный бинарник `aer-agent` (Go, без зависимостей кроме `x/sys` для Windows), ограниченная очередь, backoff, остановка отправки при отозванном токене. Установка в систему — только вручную по инструкции.
11. **Клиент**: `MonitoringController` опрашивает Core, хранит последний снимок на диске; данные помечаются live/stale. Scene получает маленькую модель `LiveStatus` через существующий Scene Binding и не знает про API/таблицы мониторинга.

## Альтернативы
- Prometheus/VictoriaMetrics/Loki — отвергнуто: лишние процессы и память для одного дома; SQLite с агрегатами укладывается в требования (замеры — `docs/M05_MONITORING_REPORT.md`).
- Beszel/Netdata как агент — возможны позже как интеграции; собственный агент нужен для единого протокола, отзыва доступа и честных `unsupported`.
- Один общий токен агентов — отвергнуто заданием (нет отзыва, возможна подмена устройства).
- ICMP-ping — отвергнуто: raw-сокеты требуют прав, а молчание ICMP не доказывает выключение.

## Последствия
- Миграции `monitoring` v1; Core тратит ≈16–26 МБ RSS; при 100 агентах — ≈5 % одного ядра.
- Агент Windows собран и проверен только кросс-компиляцией и тестами разборщиков; работа на реальной Windows не проверена (UNVERIFIED).
- Удаление сырых строк не уменьшает файл SQLite (место переиспользуется); `VACUUM` не запускается автоматически.
