# ADR-012: Боты (M06)

**Статус:** ACCEPTED (2026-10-27). Контракт `openapi.yaml` 0.6.0 → **0.7.0** (аддитивно: пути `/bots/*`, протокол заданий `POST /bots/agent/jobs`, поле `BotStatus.version`). Миграции: `bots` v1, `monitoring` v2 (только индекс).

## Контекст
Нужен единый центр для Telegram-ботов, Python-процессов, контейнеров, n8n и других автоматизаций: видеть состояние, ошибки, задания и выполнять **разрешённые** операции (старт/стоп/перезапуск, повтор задания). Ограничения: один домашний сервер, без тяжёлых зависимостей, без второго реестра устройств, без дублирования хранилища метрик/логов/инцидентов M05, без произвольного удалённого выполнения команд, секреты отдельно от Registry.

## Решения
1. **Бот = объект Registry.** Модуль Core `bots` хранит только своё: конфигурацию бота (`bot_configs`: среда, категория, адаптеры, heartbeat, источник логов), историю заданий (`bot_jobs`) и аудит действий (`bot_actions`) — по UUID объекта. Имя, тип, теги, сервер (`runs_on`), зависимости (`depends_on`), архив — в Registry. Чтобы мастер создавал бота одним запросом, Bots получает **полный сервис Registry** (`RegistryWriter`: Create/Update/Archive/Restore/AddRelation/DeleteRelation); вся валидация остаётся в Registry, таблицы Registry Bots не трогает. Если запись конфигурации не удалась после создания объекта — объект архивируется (без «полусозданных» ботов в списке).
2. **Состояние, метрики, логи, события и инциденты — только в Monitoring.** Bots читает их через сервис Monitoring и пишет через новые узкие методы (`AppendLog`, `RecordEvent`, `StoreSamples`, `RaiseIncident`/`ResolveIncident`, `SetIntegrationStatus`, `EventsOfKinds`) с теми же правилами: вырезание секретов, лимиты журнала, группировка инцидентов. Настройки, которые нужны Monitoring для проверки (`heartbeatTimeoutSec`, `container`, `url` для `/healthz` n8n), Bots записывает в `attributes.monitoring` объекта Registry — Monitoring читает их как и раньше. Пер-объектный тайм-аут heartbeat — новое поле этих атрибутов.
3. **Адаптеры — расширяемые и подключаемые.** Интерфейс `Adapter` (описание) + необязательные `Controller` (start/stop/restart + состояние среды), `Checker` (проверка соединения), `Syncer` (периодический опрос), `Retrier` (повтор задания). Встроенные: `heartbeat` (только мониторинг), `telegram`, `process`, `systemd_user`, `docker`, `n8n`. Новый язык/супервизор = новый адаптер, сервис не меняется.
4. **Всё исполняемое объявляется только в конфигурации Core** (`bots.controllers`, `bots.n8n`, `bots.telegramTokens`), проверяется при старте (абсолютный путь программы, имя юнита `*.service`, имя контейнера, список разрешённых действий `allow`, запрет секретов в `env`, n8n-URL без учётных данных). API может лишь **выбрать** объявленный элемент по ID; ни один запрос не добавляет команду, путь к файлу или URL для исполнения. Один управляющий адаптер — не больше одного активного бота.
5. **Процесс под управлением Core** (`process`): Core запускает объявленный argv без оболочки, в своей группе процессов, с минимальным окружением (переменные Core и его секреты не наследуются), пишет stdout/stderr в журнал Monitoring (уровень угадывается по тексту), меряет CPU/RSS из `/proc`, различает остановку по команде и самостоятельное завершение (событие `bot_crashed` + инцидент `bot_process:<id>` с кодом выхода). Стоп: SIGTERM группе, через `stopTimeoutSec` — SIGKILL. На Linux дочерний процесс получает SIGTERM при гибели Core (`Pdeathsig`); при штатной остановке Core останавливает своих детей; **после перезапуска Core процессы сами не запускаются**. Чужие процессы не затрагиваются: Core знает только PID, который запустил сам.
6. **systemd** — только `systemctl --user` для объявленного юнита (системные службы вне области). **Docker** — запись (start/stop/restart) только для объявленного контейнера через локальный сокет; чтение остаётся у Monitoring (ADR-011 п. 9 сохраняется для мониторинга).
7. **Действия — двухшаговые, одноразовые и с аудитом.** `POST …/actions/{a}/confirm` выдаёт одноразовое подтверждение (сводка, риски, срок жизни `confirmTtlSec`); `POST …/actions/{a}` требует его (кроме read-only `check`) и заголовок `Idempotency-Key`: повтор ключа возвращает первый результат (`replayed=true`) и ничего не исполняет, ключ другой операции — 409. Для одного бота одновременно выполняется одно действие (409), всего — не больше `maxConcurrentOps`, тайм-аут `opTimeoutSec`; операция не зависит от разрыва HTTP-соединения. Каждая попытка — выполненная, неудачная или отклонённая — записывается в `bot_actions` и в события Monitoring. Недоступное действие (только мониторинг, не в `allow`, «уже запущен») отдаётся с причиной, кнопка неактивна.
8. **Задания — универсальная модель** `pending/running/success/failed/cancelled` с длительностью, результатом и ошибкой. Источники: бот через свои учётные данные heartbeat (`POST /bots/agent/jobs`, upsert по своему id) и n8n (выполнения, read-only). Повтор — только если адаптер умеет (`n8n`, `allowRetry`) и после подтверждения; задания heartbeat-ботов повторять нечем — повтор недоступен. Хранение ограничено (`jobRetentionDays`, `jobMaxRows`), аудит — `auditRetentionDays`.
9. **n8n** — публичный REST API (`X-N8N-API-KEY` из файла, редиректы не следуют): `/healthz`, workflows, executions. Workflows не изменяются (нет вызовов активации/редактирования); единственная запись — `POST /executions/{id}/retry` после подтверждения. Новое неудачное выполнение открывает инцидент `n8n_failed:<id>`, успешное последнее — закрывает.
10. **Telegram**: токен не нужен ни для мониторинга, ни для заданий, ни для ошибок API (их сообщает бот через heartbeat). Необязательная проверка `getMe` — только с файлом токена, объявленным в конфиге; токен не покидает Core, текст ошибок HTTP-клиента (содержит URL с токеном) не используется.
11. **Список ботов** считается одним листингом Registry и кэшируется на 2 с с объединением одновременных запросов (у SQLite одно соединение; без этого 16 параллельных клиентов давали p95 ≈ 1 с). Изменения через Bots сбрасывают кэш.
12. **Клиент:** раздел «Боты» (`BotsController` + `HttpBotsApi`), действия только через `runBotAction` (подтверждение от Core → диалог → один запрос с новым ключом идемпотентности). В доме — без нового механизма привязки: объект сцены по-прежнему привязан к UUID Registry; карточка объекта получает необязательный слот, в который оболочка кладёт панель бота, если этот UUID — бот.

## Альтернативы
- Свой реестр ботов в Bots — отвергнуто требованием (один Registry).
- Команды/скрипты, задаваемые из интерфейса — отвергнуто: это произвольное удалённое выполнение; адаптеры объявляет владелец в конфиге сервера.
- Supervisor/pm2/systemd system units — тяжелее или требуют root; `process` + `systemd --user` покрывают дом без привилегий.
- Отдельные таблицы логов/метрик ботов — отвергнуто: дублировало бы M05.
- Хранить токен Telegram в Registry/UI — отвергнуто (MODULES: «хранить Telegram токены в UI» — запрещено).

## Последствия
- Без объявленных адаптеров модуль работает в режиме «только мониторинг» (интеграция «Управление ботами» = disabled).
- Windows: процесс-адаптер собирается, стоп = принудительное завершение, без метрик CPU/RAM (UNVERIFIED, M10). Docker/systemd/n8n проверены на подделках API, реальные службы не запускались.
- Добавлен индекс `mon_logs(entity_id, id)` (миграция monitoring v2): страница логов бота при 50 000 строк — 1 мс вместо 148 мс.
