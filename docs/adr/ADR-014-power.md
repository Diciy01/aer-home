# ADR-014: Питание и смена ОС — WoL из Core, фиксированные адаптеры агента, одноразовая загрузка UEFI (M08)

**Статус:** ACCEPTED (2026-10-28). Основание — `docs/S_POWER_FEASIBILITY.md`. Контракт 0.8.0 → **0.9.0** (аддитивно: `/power/*`, вид агента `power`, возможность Registry `power.suspend`). Закрывает ADR-004 «Cross-OS boot control» в части механизма; реальное переключение — после приёмки при физическом присутствии.

## Контекст
Нужно включать компьютеры по сети, выключать/перезагружать/усыплять их и переключать dual-boot ПК Ubuntu ↔ Windows. Основной ПК: UEFI, Secure Boot включён, первым в порядке загрузки стоит rEFInd (через shim), за ним Ubuntu shim и Windows Boot Manager; у владельца есть собственный проект переключения на rEFInd. Сейчас Core работает на том же ПК; постоянный сервер — этап M13. Нельзя: произвольные команды от клиента, `sudo NOPASSWD` на всё, изменение загрузчика/UEFI/BitLocker/Secure Boot из AER, автоматические повторы перезагрузки.

## Решение
1. **Модуль Core `power`** — плоскость управления: устройства поверх Registry (без своего реестра), политика владельца, цель WoL, задания с аудитом. Состояние «в сети/не отвечает» берётся у Monitoring (только чтение) и у агентов питания; Monitoring ничего не исполняет.
2. **Wake-on-LAN отправляет Core** (UDP, 6×FF + MAC×16, по умолчанию 3 пакета на порт 9). Адрес назначения — только частные диапазоны, link-local, loopback и 255.255.255.255; интерфейс выбирается по имени (привязка сокета к его IPv4). Отправка **выключена по умолчанию** (`power.wol.enabled=false`). Если MAC цели совпадает с MAC самого Core (или агента на том же ПК), включение недоступно с объяснением: выключенный ПК не включит сам себя — нужен постоянно включённый сервер (M13). Успех WoL определяется только по появлению устройства (агент/мониторинг) до тайм-аута; иначе `timeout` + инцидент.
3. **Остальные операции исполняет агент `aer-power-host`** на самом компьютере (учётка Monitoring вида `power`, отдельная на каждую ОС dual-boot ПК, отзывается мгновенно). Клиент выбирает действие из закрытого списка `wake | shutdown | reboot | suspend | switch_os | check`; Core передаёт агенту только имя действия и (для смены ОС) идентификатор загрузочной записи, **которую агент сам сообщил**. Агент повторно проверяет запись по свежей инвентаризации и запускает **фиксированный argv** своего адаптера:
   - Linux: `systemctl poweroff|reboot|suspend` (logind/polkit), `sudo -n /usr/bin/efibootmgr --bootnext XXXX` + `systemctl reboot`;
   - Windows: `shutdown.exe /s|/r /t 30`, `bcdedit /set {fwbootmgr} bootsequence {GUID}` + `shutdown.exe /r /t 30`; сон на Windows не поддерживается (честный отказ).
   Произвольного текста команды нет ни в API, ни в протоколе агента; лишние поля запроса отвергаются (400).
4. **Режим проверки по умолчанию.** Агент без `"execute": true` в своём конфиге ничего не выполняет и отвечает `simulated` с argv, который запустил бы; задание получает состояние `simulated`, интерфейс помечает его SIMULATED.
5. **Смена ОС — только одноразовая загрузка UEFI BootNext** (Linux: efibootmgr; Windows: `{fwbootmgr} bootsequence`). Постоянный порядок загрузки, GRUB, rEFInd и записи NVRAM не меняются; при сбое следующая обычная загрузка идёт по прежнему порядку. `grub-reboot` не используется: на этом ПК GRUB не первый загрузчик (rEFInd), а `grubenv` в одноразовом режиме зависит от конфигурации меню. Предпроверки: запись цели найдена и однозначна, прошивка UEFI, Secure Boot (информирование), BitLocker (`on` блокирует, пока владелец явно не разрешит в политике; `unknown` — предупреждение). Смена ОС **выключена в политике по умолчанию**. `efibootmgr --bootnext` требует root: агент работает от пользователя и вызывает только `sudo -n` на один бинарник; правило sudoers AER **не устанавливает** — без него действие недоступно с причиной.
6. **Задания**: подтверждение (одноразовый токен, привязан к устройству, действию и целевой ОС, 120 с) + `Idempotency-Key` (повтор → то же задание, другая операция → 409) + аудит каждого запроса, включая отказы. Состояния: `queued → sent → waiting → succeeded | failed | timeout | cancelled | simulated` (+ `rejected` для отказов). Одно активное задание на устройство, общий лимит. Отмена — только пока агент не забрал команду (атомарный условный переход `queued`). Результат: выключение/сон — устройство перестало отвечать (подтверждения от выключенного устройства быть не может, так и написано), перезагрузка — новый `bootId`, смена ОС — новый `bootId` и ОС = цель (иначе `failed`: «загрузилась другая ОС»). Тайм-аут — «состояние неизвестно», не успех. **Никаких автоматических повторов**; после перезапуска Core неотданные команды завершаются `failed`, не пересылаются.
7. **Ошибки → Monitoring**: события `power_job`, инцидент `power:<устройство>:<действие>` при `failed/timeout` (уведомления — по правилам M05), закрытие инцидента при следующем успехе.

## Альтернативы
- `grub-reboot` — работает только когда GRUB первый и `GRUB_DEFAULT=saved`; изменяет `grubenv` на диске; Windows → Ubuntu всё равно требует BootNext. Отклонено как основной механизм.
- Управление rEFInd (`PreviousBoot` в `vars/` на ESP) — запись на ESP из AER; отклонено.
- Отправка WoL агентом соседнего ПК — нет гарантированно включённого соседа; отложено до M13 (сервер).
- Выполнение команд по SSH из Core — хранение ключей с правами root в Core; отклонено.

## Последствия
- Реальные выключение, перезагрузка, сон, BootNext и WoL **не выполнялись** при разработке; всё — на подделках и в режиме проверки (SIMULATED). Приёмка — при физическом присутствии владельца (`docs/POWER_DUALBOOT.md`, раздел «Приёмка»).
- Windows-агент собирается и покрыт тестами разбора `bcdedit`/`manage-bde`, но на Windows не запускался (UNVERIFIED); чтение `{fwbootmgr}` и BitLocker требует прав администратора.
- Пока Core на том же ПК, WoL для него недоступен — это показывается в интерфейсе, а не скрывается.
