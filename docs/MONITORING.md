# Мониторинг (M05)

> M06: боты используют это же хранилище через хуки сервиса (`AppendLog`, `RecordEvent`, `StoreSamples`, `RaiseIncident`/`ResolveIncident`, `SetIntegrationStatus`, `EventsOfKinds`) — `docs/BOTS.md`, ADR-012.

Что работает, что сломалось, что недоступно и где искать причину. Решения — ADR-011; агенты — `docs/AGENTS.md`; замеры — `docs/M05_MONITORING_REPORT.md`.

## Архитектура

```text
 aer-agent (Ubuntu/Windows) ──report──┐           ┌── Registry (registry.Reader, только чтение)
 heartbeat бота (aer_heartbeat.py) ───┤           │
                                      ▼           │
                        Core: модуль monitoring ◄─┘
   ┌───────────────┬──────────────┬─────────────┬──────────────┬──────────────┐
   │ Ingest        │ Checks       │ Docker      │ Incidents    │ Notifier     │
   │ метрики, логи │ агенты, HTTP │ сокет, RO   │ группировка, │ центр +      │
   │ redact, лимит │ TCP, боты    │ stats, logs │ пороги, ack  │ Telegram(опц)│
   └──────┬────────┴──────┬───────┴──────┬──────┴──────┬───────┴──────┬───────┘
          ▼               ▼              ▼             ▼              ▼
                SQLite: mon_samples · mon_rollups · mon_latest · mon_state · mon_logs
                        mon_incidents(+events) · mon_events · mon_notifications · mon_containers
          │
          ▼  /api/v1/monitoring/*  (токен владельца)
   Flutter: раздел «Мониторинг», диагностика устройства, колокольчик, статусы в доме
```

Фоновый цикл (`Run`) работает в процессе Core независимо от клиентов: проверки доступности (по умолчанию каждые 30 с, не больше 8 параллельно, тайм-аут 5 с), опрос Docker (30 с, stats — 60 с), отправка уведомлений (30 с), очистка (раз в час).

## Состояния

| Состояние | Когда |
|---|---|
| `online` | агент/бот прислал данные в пределах `heartbeatTimeoutSec`; HTTP 2xx/3xx; TCP ответил (или отказал в соединении — хост в сети); контейнер `running` |
| `degraded` | работает, но есть проблема: открыт инцидент по порогу (диск, температура, служба), HTTP 4xx/5xx или ошибка TLS, бот сообщает о сбое зависимости или последняя операция завершилась ошибкой, контейнер `unhealthy/restarting/paused` |
| `offline` | `failuresBeforeOffline` подряд неудачных проверок цели, которая раньше отвечала (агент замолчал, сайт перестал отвечать, контейнер остановлен) |
| `unknown` | нет данных: агент ни разу не подключался, нет адреса и агента, Docker недоступен, DNS не разрешается, цель ни разу не ответила (может блокировать проверки) |
| `unsupported` | тип без способа проверки (виртуальный объект) или мониторинг выключен в атрибутах |

Отдельно различаются «нет данных» (`unknown`), «ошибка проверки» (причина в `reason`) и «реально недоступен» (`offline`). Последний контакт хранится всегда; при недоступности показывается последнее известное время, текущие значения выключенного ПК не запрашиваются.

Переопределения в Registry: `attributes.monitoring = {"disabled": true, "ports": [22], "url": "https://…", "container": "имя", "heartbeatTimeoutSec": 45}`. `heartbeatTimeoutSec` (M06) — собственный тайм-аут агентов объекта (его выставляет Bots из настроек бота). Для ботов, приложений, процессов, служб и автоматизаций без heartbeat используется `container` (Docker), затем `url` (HTTP, для n8n — `/healthz`), иначе «неизвестно».

## Метрики
Каталог — `GET /monitoring/metric-types` (CPU, память, swap, заполнение и свободное место дисков, сеть приём/передача/ошибки, температуры CPU/GPU, загрузка GPU, uptime, число процессов, состояние служб, ресурсы процесса бота, доступность API Telegram, Docker CPU/RAM/сеть). Каждое значение: устройство, метрика, метка (точка монтирования, интерфейс, служба), значение или `null`, единица, время, источник, `quality` (`ok`/`unsupported`/`unavailable`) и причина отсутствия.

## Хранение и очистка

| Данные | Таблица | Срок по умолчанию | Настройка |
|---|---|---|---|
| Сырые значения | `mon_samples` | 7 дней | `rawRetentionDays` |
| 5-минутные агрегаты (min/max/avg) | `mon_rollups` | 30 дней | `rollupRetentionDays` |
| Текущие значения | `mon_latest` | не удаляются | — |
| Логи (индекс `(entity_id, id)` — миграция v2, M06) | `mon_logs` | 14 дней и не больше 200 000 строк | `logRetentionDays`, `logMaxRows`, `logRatePerMin` (600/мин на источник) |
| Решённые инциденты (с хронологией) | `mon_incidents`, `mon_incident_events` | 365 дней; `0` — навсегда; открытые не удаляются | `resolvedIncidentDays` |
| История событий | `mon_events` | max(30, rollup) дней | — |
| Уведомления | `mon_notifications` | 90 дней | `notificationRetentionDays` |

Агрегаты пишутся в той же транзакции, что и сырое значение, поэтому удаление сырых строк не оставляет графики пустыми. Графики: до 6 ч в пределах хранения сырых данных — исходные измерения, иначе 5-минутные агрегаты с полосой min–max; до 400 точек; интервалы без данных — `null` (разрыв линии).

Конфигурация — раздел `monitoring` JSON-конфига Core (пример: `deploy/core-monitoring.example.json`); недопустимые значения отклоняются при запуске.

## Инциденты
- Ключи: `availability:<entity>`, `disk_low:<entity>:<mount>`, `cpu.temperature:<entity>`, `gpu.temperature:<entity>`, `service_down:<entity>:<unit>`, `bot_api:<entity>`, `container:<name>`, `integration:docker`; от Bots (M06): `bot_process:<entity>` (процесс под управлением Core завершился сам), `n8n_failed:<entity>` (новое неудачное выполнение n8n).
- Один нерешённый инцидент на ключ; повторы — `occurrences` и запись «повтор» в хронологии не чаще раза в 10 минут.
- Статусы: `open` → (`acknowledged`) → `resolved`. Восстановление закрывает инцидент автоматически (в т.ч. подтверждённый).
- Серьёзность доступности: `critical` для сервера, роутера, сайта, БД, контейнера, бота, сетевого устройства, хранилища; `warning` для ПК и прочего. Пороги: свободно < 10 % — предупреждение, < 5 % — критично (закрытие при > 12 %); температура ≥ 90 °C (закрытие < 85 °C); 2 замера подряд.
- `cause` — только из прямых данных; `related` — корреляция по связям Registry (`runs_on`, `hosted_by`, `depends_on`, `installed_on`) с открытыми инцидентами доступности, явно не причина.

## Логи
Источники: Core (warning+ через `logging.Sink`), агенты (journald warning+ / Windows Event Log), Docker (смена состояния и последние строки stderr при остановке), боты (ошибки через heartbeat), события мониторинга. Поиск по словам (сообщение и источник), фильтры по уровню (минимальный), устройству, источнику, инциденту и периоду, курсорная пагинация. Перед записью вырезаются токены Telegram, `Bearer/Basic`, `password=… token=… api_key=…` и т.п., учётные данные в URL, приватные ключи, токены агентов AER и длинные hex-ключи; значения полей с «секретными» именами заменяются целиком.

## Уведомления
Центр уведомлений: открытие инцидента и восстановление (`notifyRecovery`), без повторов на каждый замер. Telegram (необязательно): `monitoring.telegram = {enabled, botTokenFile, chatId, minSeverity}`; токен только в файле; ожидающие сообщения отправляются одним сгруппированным сообщением раз в 30 с; статус каждого уведомления: `disabled/pending/sent/skipped/failed`. Без явного включения ничего не отправляется.

## Интеграции
- **Docker** — только чтение: список, inspect, stats, хвост stderr. Сокет — локальный (`/var/run/docker.sock`), TCP запрещён. Нет доступа — причина видна в интерфейсе («сокет не найден», «нет прав, нужна группа docker»). Контейнер связывается с объектом Registry типа `docker_container` по имени (или `attributes.monitoring.container`); несвязанные контейнеры видны в списке и создают свои инциденты при остановке.
- **Telegram-боты** — heartbeat через учётные данные типа `bot` (`tools/bot-heartbeat/aer_heartbeat.py`): успешные действия, ошибки, проверка зависимости (API Telegram). «Процесс жив» ≠ «бот работает»: без heartbeat бот — `unknown`/`offline`, при ошибках — `degraded`. Токен бота в AER не передаётся.
- **Сайты** — HTTP GET (тайм-аут, до 5 переадресаций, читается не больше 1 КБ).
- **Сетевые устройства, ТВ, БД** — TCP-достижимость (порты из адреса или `attributes.monitoring.ports`, иначе 80/443/22/53 параллельно). Для БД проверяется соединение, не аутентификация.

## API (все пути — под `/api/v1`, контракт 0.6.0)
Токен владельца: `GET /monitoring/overview`, `GET /monitoring/metric-types`, `GET /monitoring/states`, `GET /monitoring/states/{entityId}`, `GET /monitoring/states/{entityId}/history?metric=&label=&from=&to=`, `GET /monitoring/logs`, `GET /monitoring/logs/{id}`, `GET /monitoring/events`, `GET /monitoring/incidents`, `GET /monitoring/incidents/{id}`, `POST /monitoring/incidents/{id}/acknowledge`, `GET /monitoring/notifications`, `POST /monitoring/notifications/read`, `GET/POST /monitoring/agents`, `POST /monitoring/agents/{id}/revoke`, `GET /monitoring/docker/containers`.
Токен агента: `POST /monitoring/agent/report`.

## Клиент
Раздел «Мониторинг»: Обзор (счётчики, домашний сервер, основной ПК, боты, источники данных, последние события), Устройства (карточки), Инциденты, Журнал, Агенты и интеграции; диагностика устройства (Обзор, Метрики, Графики, Логи, Инциденты, История событий); колокольчик уведомлений. Без связи с Core показывается последний снимок (`monitoring-cache.json` рядом с кэшем сцены) с временем и пометкой «устарело», действия неактивны. В доме значок привязанного устройства берёт состояние из мониторинга; в карточке — последний контакт, число инцидентов и кнопка «Диагностика».
