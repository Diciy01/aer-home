# AER Connect: первый запуск без настройки клиента

Пакет владельца содержит `connect.json` рядом с `AER-Connect.exe`: только HTTPS-адрес
Gateway и SHA-256 его сертификата. Приватных ключей, owner token, общего пароля
или общего кода регистрации в пакете нет. Распространяйте весь пакет через
доверенный канал: подмена EXE или конфигурации нарушает первоначальное доверие.

На втором ПК достаточно распаковать папку и запустить приложение. Оно создаёт
собственный X25519-ключ и идентификатор установки, сохраняет их в DPAPI и само
подаёт заявку через закреплённый TLS. Вводить адрес, отпечаток или код не нужно.
Существующая регистрация загружается из защищённого профиля, не заменяется.

## Что делает владелец

Один раз на сервере настраивает Core/Gateway, отдельную учётку Gateway и
формирует пакет с адресом и отпечатком. Для каждой новой установки один раз
разрешает её **на сервере**. Непроверенные установки не получают учётных данных.
Этот шаг сохраняет прежнее право владельца решать, какие устройства допускаются
к его серверу, и заменяет передачу кода каждому пользователю.

Windows, обычный PowerShell на сервере:

```powershell
& .\tools\windows\manage-connect-registrations.ps1 -Action List
& .\tools\windows\manage-connect-registrations.ps1 -Action Approve -RequestId ID_ЗАЯВКИ -Fingerprint SHA256_КЛЮЧА
# Либо отклонить:
& .\tools\windows\manage-connect-registrations.ps1 -Action Reject -RequestId ID_ЗАЯВКИ
```

По умолчанию команды используют только отдельный локальный стенд
`E:\dev\runs\aer-anywhere-manual-20261029\core.json` (порт 18987). Другую
конфигурацию владелец может явно указать через `-CoreConfig`. Учётные данные
читаются в память на сервере, не передаются в аргументах и не печатаются.
Не распространяйте этот инструмент или каталог состояния вместе с клиентом.

Заявка содержит имя и SHA-256 ключа. Имя не доказывает принадлежность компьютера:
разрешайте только ожидаемую установку; её ключ доступен в «Сведения об устройстве»
на экране ожидания. Заявка действует 24 часа. Решение владелец принимает через
owner API, который отсутствует на публичном Gateway.

Ubuntu: `sudo aer-admin registrations`, затем
`sudo aer-admin approve-registration REQUEST_ID` либо `reject-registration`.

После одобрения клиент продолжает сам, обычно в течение 10 секунд. Появляются
ID компьютера, временный пароль и статус Host. Пользователь другого
зарегистрированного ПК вводит ID и пароль и нажимает «Подключиться».

## Постоянный доступ

Регистрация на сервере **не** предоставляет управление чужими компьютерами и
не включает постоянный пароль или доверие устройств. Для неизвестного клиента
нужны правильный пароль и прежнее локальное подтверждение сеанса. Владелец
домашнего ПК отдельно включает постоянный доступ доверенным устройствам,
разрешает ключ рабочего ПК и при необходимости включает постоянный пароль.
Отзыв, локальный Stop и ограничения Windows desktop остаются прежними.

## Протокол `aer-connect-registration/1`

- `POST /gw/v1/devices/registration`: имя, открытый ключ, отпечаток установки.
  Ответ `verifying` содержит зашифрованный случайный challenge.
- Клиент открывает challenge своим ключом и повторяет запрос с `proof`.
  Только после проверки владения ключом заявка получает статус `pending` и
  появляется владельцу в `GET /api/v1/remote/registrations`.
- Owner API `POST /remote/registrations/{id}/approve` или `/reject` принимает
  решение. На Gateway этих административных маршрутов нет.
- После одобрения выдаётся прежняя пара credentials Host/Viewer, зашифрованная
  только для этой установки. Используются X25519, HKDF-SHA256 и AES-256-GCM с
  отдельным доменом, ID заявки, instance и ключом получателя. На сервере
  сохраняется зашифрованный ответ и хэш proof, не открытые credentials.
- Повтор запроса и перезапуск возвращают тот же ответ и тот же ID устройства.
  Клиент сохраняет итоговый профиль в DPAPI. Отозванное устройство, credential
  или конфликт установки запрещают повторное получение ответа.
- Публичные запросы ограничены на Gateway (60/мин/IP); новые заявки дополнительно
  ограничены на Core (5/10 мин/IP, до 128 одновременно ожидающих). Ошибки
  идентичности учитываются существующей защитой от перебора. Закрепление TLS
  обязательно, ошибка сервера не переключает клиента на иной способ авторизации.

Схема Remote увеличена до 5; существующие кодовая регистрация и сопряжение
сохранены для пакетов без preset и для совместимости. При старом сервере клиент
показывает ошибку; автоматического ослабления проверки нет.

Проверено локально: реальный Core + TLS Gateway, автоматические заявки двух
устройств, синтетический Host, неверный пароль/сертификат, соединение и завершение;
сохранение/отзыв, Go/Dart crypto vector, widget/golden и прежние UI-состояния.
Захват реального рабочего стола и соединение через интернет новой версии
**UNVERIFIED**. Публикация Gateway, Firewall и роутер автоматически не меняются.
