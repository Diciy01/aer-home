# S-Remote — исследование осуществимости удалённого доступа (M07.1)

Дата: 2026-10-27. Машина: Ubuntu 24.04.5 LTS, GNOME Shell 46.0 (mutter 46.2), сеанс **Wayland**, AMD Radeon RX 570, 12 потоков. Windows-машины и мобильных устройств в испытании не было.

Статусы: **VERIFIED** — проверено собственным испытанием на этой машине; **PARTIALLY VERIFIED** — проверена часть или на изолированном стенде, а не в «живом» сеансе пользователя; **UNVERIFIED** — не испытано (только документация/анализ); **BLOCKED** — невозможно без запрещённых изменений или принципиально; **UNSUPPORTED** — технология это не умеет.

## 1. Стенд (как проверялось)
Чтобы не трогать сеанс, настройки и службы пользователя, собран **изолированный стенд** (скрипты — `tools/remote-lab/`):
- **Тестовый хост** — отдельный `gnome-shell --wayland --headless --virtual-monitor 1920x1080` в собственной шине D-Bus (`dbus-run-session`), с собственными `XDG_CONFIG/DATA/CACHE_HOME` и `GSETTINGS_BACKEND=keyfile`; в нём — `gnome-remote-desktop-daemon --headless` на тестовом порту 33891 с самоподписанным сертификатом и случайным паролем.
- **Тестовый клиент** — `Xvfb :77` (свой X-сервер и свой буфер обмена) + Remmina 1.4.43 (FreeRDP 3.32) со своими каталогами конфигурации и шиной D-Bus без автозапуска служб (не трогает связку ключей пользователя).
- Ввод в клиент — `xdotool` в `:77`; результат — снимки экрана `:77` (то, что видит пользователь клиента).
Ограничение стенда: петля на одной машине (localhost), хост — headless-сеанс GNOME, а не реальный вошедший пользователь. Пользовательская служба `gnome-remote-desktop` (выключена у пользователя) не включалась; пакеты не ставились; Wayland не отключался.

### Найдено при интеграции агента (M07.3, VERIFIED на стенде)
- **gnome-remote-desktop читает учётные данные один раз — при запуске демона.** После `grdctl rdp set-credentials` работающий демон продолжает принимать **старый** пароль и отклоняет новый. Поэтому агент AER запускает демон на каждый сеанс (после записи нового пароля) и останавливает его при завершении; простая ротация через `grdctl` небезопасна.
- `grdctl rdp set-credentials` в GNOME 46 принимает пароль только аргументом командной строки (без stdin) — пароль сеанса на доли секунды виден процессам того же пользователя.
- **Remmina искажает пароль из `rdp://`-URI**, если он похож на base64 и раскодируется в кратное 8 число байт (принимает его за свой зашифрованный пароль): пароли из 32 и 64 символов отклонялись, из 24/30/36/44 — проходили. Агент выдаёт 30 буквенно-цифровых символов (≈178 бит).
- «Подключён» у агента = установленное TCP-соединение с портом RDP; неудачная аутентификация даёт кратковременное соединение — агент видит его и тут же разрыв.

## 5. Ограничения Ubuntu GNOME Wayland
- Никакого захвата и ввода «в обход»: либо RDP-сервер GNOME, включённый владельцем сеанса, либо портал с диалогом согласия на каждый сеанс.
- **Экран блокировки**: RDP-сервер GNOME в режиме общего доступа показывает экран блокировки сеанса; обходить его AER не будет. Удалённый вход «без пользователя» — системный режим GDM (`grdctl --system`, Ubuntu 24.04+) — требует root и системной службы → вне M07 (BLOCKED без разрешения).
- Список окон приложений — нет публичного API (BLOCKED); выбор окна — только диалог портала.
- Ввод через портал RemoteDesktop не ограничивается одним окном → **отдельное окно не изолирует приложение** (BLOCKED как изоляция).
- Передача файлов в RDP GNOME — только через буфер обмена (FUSE), без папок и перетаскивания.

## 6. Ограничения Windows (UNVERIFIED — проверка только на Windows, см. `docs/REMOTE_WINDOWS_VALIDATION.md`)
- RDP-хост: только Pro/Enterprise/Education; при подключении локальный сеанс блокируется (один интерактивный сеанс на клиентской Windows).
- Учётные данные RDP — учётная запись Windows: AER **не меняет** пароль пользователя Windows на сеанс → одноразовых паролей на Windows-хосте нет (вход — данными пользователя, NLA).
- RemoteApp (одно приложение) — только серверные редакции/RDS; на клиентской Windows официально нет.
- Защищённые окна (UAC, DRM) в захвате API — чёрные; RDP показывает UAC в защищённом рабочем столе по настройкам.
- Буфер обмена и диски (`drivestoredirect`) в `mstsc` — встроены.

## 7. Выбранная архитектура
- **Транспорт: RDP** (ADR-013). Ubuntu-хост — gnome-remote-desktop, управляемый агентом AER через `grdctl`; Windows-хост — встроенный RDP (агент только сообщает готовность). Клиент Linux — **внешний клиент Remmina** (запускается AER с закреплённым сертификатом и паролем сеанса; это явно показано в интерфейсе), клиент Windows — `mstsc` (UNVERIFIED).
- **AER Core — только плоскость управления**: хосты, политики, сеансы, одноразовая выдача данных подключения, отзыв, аудит. Видео, ввод и буфер обмена идут напрямую клиент ↔ хост по RDP/TLS; Core их не видит.
- **Агент хоста `aer-remote-host`**: отдельные учётные данные устройства (агент вида `remote`); на каждый одобренный сеанс — случайный пароль RDP, включение RDP-сервера; при завершении/отзыве/истечении — выключение сервера и очистка пароля. Порт RDP открыт **только во время сеанса**.
- **Файлы**: собственный канал AER — HTTPS прямо к агенту хоста (сертификат закрепляется через Core), токен сеанса, только папка обмена, лимит размера, SHA-256, без хранения на Core.
- **Буфер обмена**: канал RDP (проверен); отключение — на стороне клиента (настройка запуска) — ограничение: сервер GNOME не умеет запрещать буфер на сеанс.
- **Remote Apps (мобильные)**: архитектура и API готовятся, функция — UNSUPPORTED до отдельного транспорта (портал ScreenCast окна + WebRTC) и проверки изоляции ввода.

## 9. Требования безопасности (вывод исследования)
Отдельная идентификация хоста; пароль RDP на один сеанс, выдаваемый клиенту один раз; сервер RDP включён только во время сеанса; закрепление сертификата хоста; подтверждение на хосте (по политике); отзыв за доли секунды; ограничение времени сеанса агентом даже без Core; сеть — локальная или VPN (Tailscale), без проброса портов в интернет. Подробно — `docs/REMOTE_SECURITY.md`.
