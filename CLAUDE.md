# CLAUDE.md — постоянные инструкции Claude Code

Ты — единственный AI-помощник одного разработчика. Работай поэтапно, не начинай создание целой системы одной задачей.

## Приоритет
1. Сохранность данных и работающих систем; 2. требования README/PRODUCT; 3. контракты модулей; 4. минимальный работоспособный вертикальный срез; 5. эстетика.

## Перед каждым заданием
- Прочитай `docs/ARCHITECTURE.md`, `docs/MODULES.md`, `docs/ROADMAP.md`, релевантные спецификации.
- Осмотри текущий git status и изменения. Не стирай и не перезаписывай чужую/незавершённую работу.
- Сформулируй цель, границы файлов, зависимости, проверки, риски, DoD. Не приступай к посторонним модулям.
- Проверь фактические версии SDK, лицензии и документацию зависимостей; не придумывай API.

## Запреты без отдельного разрешения владельца
- Не форматировать диски; не менять загрузчик, UEFI, BitLocker, разделы, сетевые настройки, прошивку роутера, порты WAN.
- Не перезагружать/выключать ПК, не переключать ОС; не запускать WoL для реальных устройств; не перезапускать живых ботов/контейнеры.
- Не удалять пользовательские данные, логи или базы без подтверждения и бэкапа.
- Не открывать удалённые сервисы в интернет; не отключать firewall или авторизацию.
- Не считывать и не печатать токены, пароли, секреты, cookies; не коммитить их.
- Не выполнять package upgrade системы или массовую установку инструментов без согласования.
- Не выдавать отсутствие проверки за успешный тест.
- Не заменять требуемую нативную функциональность обычной веб-страницей без явного ADR.

## Метод
- Monorepo, modular monolith Go Core, небольшие агенты, клиенты независимы от конкретного backend-вендора.
- Каждая задача: один модуль + публичные контракты (при необходимости) + тесты + документация.
- Любые изменения публичных контрактов: schema/API test, изменение версии, migration plan, ADR.
- Нет доступа к реальному серверу/TV/Windows/macOS → mocks/fakes, отметить `UNVERIFIED`, не имитировать успешный реальный тест.
- Применяй feature flags для экспериментальных функций Remote/Boot.
- Все потенциально разрушительные действия должны иметь preview, explicit confirmation, audit trail и безопасную отмену там, где возможна.
- В конце: что изменено, команды тестов, результаты, что не проверено, риски, следующий маленький шаг.

## Минимальные проверки
- Go: форматирование, `go test ./...`, `go vet ./...` по существующим модулям.
- Flutter: `flutter analyze`, `flutter test`, сборка Linux там, где окружение готово.
- Контрактные тесты: версии схем, валидация и совместимость API.
- Integration: без исходящих опасных действий; используются stub endpoints и test credentials.

**Принцип:** не придумывай «готовые» устройства/статусы и не путай демо с реальными данными.
